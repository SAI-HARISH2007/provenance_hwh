# Incident Report: Payments API Clock Skew After Node Reboot

## Summary
At 03:12 UTC, a P1 alert fired for high 401 rates on `/v1/checkout` (`api-gateway`), with `payments-api` showing degraded status. Investigation revealed that `payments-api` host `payments-3` suffered a kernel patch reboot at 02:02 UTC. Following the reboot, `chronyd` was not running on the node, causing a clock drift of -412.3 seconds. Because `auth-api` recently switched to ES256 JWT signing with strict issued-at checks, tokens generated by `auth-api` (correct UTC time) appeared to be issued in the future to `payments-api`, resulting in `InvalidIssuedAt` JWT validation failures and massive 401 errors.

## Timeline
- **02:02 UTC**: `payments-api` node `payments-3` rebooted after kernel patch (ops-bot). `chronyd` failed to start automatically.
- **02:39 UTC**: `auth-api` deployed `auth-1.6.0` switching JWT signing to ES256 (dual-verify enabled).
- **03:02 UTC**: Error rate on `payments-api` spiked from ~0.4% to ~90% as tokens received from auth started failing validation due to clock drift.
- **03:12 UTC**: P1 alert fired on `api-gateway`.

## Root Cause
`clock_skew`: The host running `payments-api` (`payments-3`) drifted by ~412 seconds behind actual time because `chronyd` was not running after the node reboot. This caused JWT `iat` (issued-at) validation to reject valid tokens as issued in the future.

## Evidence
1. **Clock Probe**: `run_probe` on `payments-api` (`payments-3`) reported `ntp offset -412.3s — chronyd not running`. Probes on `auth-api` and `postgres` showed near-zero offset.
2. **Logs**: `query_logs` on `payments-api` showed repeated `jwt verification failed: InvalidIssuedAt` errors for ES256 tokens.
3. **Metrics**: `get_metrics` showed `payments-api` error rate jumping sharply around 03:02 UTC.

## Proposed Remediation
Sync the clock on `payments-api` (`payments-3`) and start `chronyd`. This is safe and immediately resolves the clock drift causing the token validation failures.

## Follow-ups
- Ensure `chronyd` is enabled and started on boot for all re-provisioned/rebooted Kubernetes worker nodes.
- Investigate why systemd/chronyd failed to start automatically on node `payments-3`.
