# Incident Report: Orders-API and Inventory-API Failure

## Summary
At 2026-08-30T03:12:00.000Z, `orders-api` experienced a P1 alert due to an order creation failure rate of ~58%. Investigation revealed that the underlying PostgreSQL database hit 100% disk utilization, preventing database writes and failing transactions across dependent services.

## Timeline
- **2026-08-30T01:02:00Z**: Config change enabled `log_min_duration_statement=0` on PostgreSQL for slow-query investigation.
- **2026-08-30T02:47:53Z**: First database extension error logged by `orders-api` (`could not extend file`).
- **2026-08-30T02:52:00Z**: `inventory-api` deploy (`inventory-1.9.3`) introduces reservation retries.
- **2026-08-30T03:12:00Z**: P1 alert fires for `orders-api` as failure rate reaches 58%.

## Root Cause
The PostgreSQL database ran out of disk space (`disk_pct: 100`), likely driven by excessive log generation from `log_min_duration_statement=0` combined with standard database growth. This caused write operations to fail with `could not extend file` errors.

## Evidence
- PostgreSQL metric `disk_pct` is at `100`.
- `orders-api` logs repeatedly show: `ERROR orders-api: insert failed: could not extend file "base/16384/2619"`.
- Recent config change enabled verbose query logging (`log_min_duration_statement=0`).

## Remediation
1. Free disk space on the PostgreSQL server (e.g., truncate or clear heavy log files generated by `log_min_duration_statement=0`, remove unnecessary temp files or old backups).
2. Revert the logging configuration (`log_min_duration_statement` to a reasonable threshold or default) once space is recovered.

## Follow-ups
- Implement disk space and log volume monitoring/alerting before 100% exhaustion.
- Review logging policies to prevent verbose statement logging from filling up production disks.
